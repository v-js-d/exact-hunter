# Руководство по работе с Trunk‑Based Development

Документ описывает правила работы команды с git и процессом разработки.
Цель - уменьшить конфликты, ускорить интеграцию кода и сделать релизы предсказуемыми.

---

# 1. Основная идея

В проекте существует ОДНА основная ветка: `trunk` (main / master / dev).

Вся разработка постоянно интегрируется в неё маленькими частями.

Мы НЕ разрабатываем фичи неделями в отдельных ветках.
Мы постоянно вливаем небольшие изменения через Pull Request.

Главное правило:

> Код в trunk всегда должен собираться и запускаться.

---

# 2. Основные принципы

1. Короткоживущие ветки (до 1 дня)
2. Маленькие Pull Requests
3. Частые merge в trunk
4. Feature flags для незавершённого функционала
5. CI - обязательная проверка
6. Нельзя ломать trunk

---

# 3. Ежедневный workflow разработчика

## 1. Обновиться от trunk

```
git checkout trunk
git pull
```

## 2. Создать короткую ветку

Название:
```
feat/...
fix/...
refactor/...
chore/...
```

```
git checkout -b feat/cart-service
```
## 2.1 Что значит feat/ fix/ refactor/ chore/

Это типы изменений.
Они нужны, чтобы по названию ветки и PR было понятно что ты вообще делаешь - без открытия кода.

Это упрощённая версия Conventional Commits (и её почти все команды используют вместе с trunk-based).

```
feat/ - новая функциональность
```

Примеры

```
feat/login-form
feat/cart-calculation
feat/profile-avatar-upload
feat/notifications-socket
```

---

```
fix/ - исправление бага
```

```
fix/header-overflow
fix/payment-validation
fix/mobile-scroll
fix/crash-on-empty-list
```

---

```
refactor/ - переписывание без изменения поведения
```

```
refactor/api-client
refactor/useAuth composable
refactor/store structure
```

---

```
chore/ - технические изменения
```

```
chore/eslint-config
chore/update-deps
chore/docker-config
chore/ci-cache
```

## 3. Сделать маленький законченный шаг

Изменение должно:
- компилироваться
- не ломать приложение
- проходить тесты

## 4. Открыть Pull Request

В тот же день.

## 5. После ревью - merge и удалить ветку

---

# 4. Что считается правильным размером PR

Хороший PR:
- до ~300 строк
- можно понять за 5-10 минут
- содержит один логический шаг

Плохой PR:
- "реализовал всю авторизацию"
- 2000+ строк
- невозможно проверить

---

# 5. Как делать большие фичи

Большие фичи делятся на интегрируемые шаги.

Пример: новая корзина

1. Добавить feature flag
2. Добавить API клиент
3. Добавить store
4. Добавить UI (скрытый)
5. Подключить логику
6. Включить флаг для команды
7. Включить флаг пользователям
8. Удалить старую реализацию

Каждый пункт - отдельный PR.

---

# 6. Feature Flags

Feature flag - переключатель, позволяющий скрыть незавершённый функционал.

Пример:

```
if (features.newCheckout) {
  renderNewCheckout()
} else {
  renderOldCheckout()
}
```

Правила:
- незавершённые фичи только под флагом
- после релиза флаг удаляется
- флаги не живут месяцами

Feature flag не нужны если:
- задача ≤ 4 часа, максимум в рабочий день успеваем
- нет больших изменений в UI
- нет изменений поведения

---

# 7. Правила Pull Request

Перед merge обязательно:
- CI зелёный
- минимум 1 code review
- приложение запускается

Запрещено:
- пушить напрямую в trunk
- мержить красный CI
- большие PR

---

# 8. Code Review ожидания

Ревьюер проверяет:
- читаемость
- архитектуру
- побочные эффекты
- соответствие задаче

Ревью НЕ блокирует на мелочах - создаются follow‑up задачи.

---

# 9. Definition of Done

Задача считается завершённой если:

- код в trunk
- CI зелёный
- поведение не сломано
- фича скрыта флагом (если не готова)

---

# 10. Что запрещено

- ❌ Долгие feature‑ветки
- ❌ "Сначала сделаю всё - потом PR"
- ❌ Рефакторинг + фича в одном PR
- ❌ Ломать существующее поведение
- ❌ Откладывать merge на дни

---

# 11. Когда включается QA

QA тестирует через feature flags.

Функционал появляется раньше релиза.

---

# 12. Частые вопросы

## Если фича не готова?
Скрыть под feature flag.

## Если PR маленький и не идеальный?
Мержим. Улучшаем следующими PR.

## Если конфликт?
Обновиться от trunk и решить сразу.

---

# Итог

`Trunk‑Based Development` = `маленькие изменения` -> `частые merge` -> `стабильный trunk` -> `быстрые релизы`
